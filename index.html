Overview

Julie is a 4-stage pipeline (2 AI agents + 2 processing stages) that discovers trending products across 25 Amazon marketplaces, analyzes review sentiment, compares prices, and generates ranked purchase recommendations — all in real time.

Key highlights:

Across the Americas, Europe, Middle East & Africa, and Asia-Pacific.

What Julie Does Simple English

When you type a product query and click Analyze, here is exactly what happens:

  1. Julie opens a headless Chrome browser and searches Amazon for your query in the selected marketplace — just like a real user would, but faster. Sponsored/ad tiles are silently skipped. Multiple browser tabs run in parallel to fetch ~5 products at once (takes ~50 seconds total).
  2. Julie filters the results using three tiers: products with a monthly-purchases badge + 4★ or higher go to the top ("Trending"), followed by Best Sellers ranked by review volume, with a safety fallback that blocks anything with ≥ 30% negative reviews.
  3. Julie reads the customer reviews for each product, filtering to only those posted within your chosen review window (default: last 90 days). It sends those reviews to Amazon Bedrock — Claude Haiku 4.5 for sentiment summaries and Nova Micro for fast theme extraction — to produce pros/cons and a review score.
  4. Julie checks the price and star rating, normalises prices to USD for comparison, and produces a price-competitiveness score and a rating score.
  5. Julie scores and ranks all products using four weighted factors: review quality (35%), star rating (25%), price (20%), and trend signal (20%). The final ranked list — along with every agent's "thoughts" — streams back to your browser via the live dialogue feed.

What Each Agent Does

Agent 1 — Discovery (discovery.py)

Launches a headless Chrome browser and scrapes Amazon search result pages for the given query + marketplace. Runs multiple tabs in parallel (pool size 8 by default) to drastically reduce latency.

Discovery tiers (products must pass at least one):

TierCriteria
Trending≥ 100 monthly purchases badge and ≥ 4.0★, OR ≥ 3 recent reviews and ≥ 4.0★ avg
Best SellerRanked by 4.0★ × log(review_count)
Guarded FallbackAdmits products that do not have ≥ 30% negative reviews
ℹ️

Sponsored tile filtering: Sponsored/ad tiles are silently skipped unless they carry a genuine organic star rating and review count. This prevents ads from contaminating the results.

Monthly purchases badge: The scraper extracts "X bought in past month" badges where present — this feeds the Trending tier gate.

Agent 2 — Review Intelligence (review.py)

For each discovered product, fetches the product detail page and extracts:

  • Rating histogram (1★–5★ counts)
  • Recent reviews filtered to the configured review window (7–366 days)
  • Sends review text to Amazon Bedrock Claude Haiku 4.5 for sentiment analysis and a synthesised pros/cons summary
  • Sends review text to Amazon Bedrock Nova Micro for fast, cheap theme extraction (topics, keywords)

The review score (weight 0.35) is the dominant factor in the final recommendation score.

Agent 3 — Price & Rating (pricing.py)

Cross-checks the product's price and rating against the scraped marketplace data. Normalises prices to USD for comparison, detects the currency from the scraped price string (see Currency Auto-detection), and produces a normalised price score (weight 0.20) plus a raw rating score (weight 0.25).

Agent 4 — Recommendation (recommendation.py)

Combines the three upstream scores with the trend signal (weight 0.20) into a single composite score, sorts products, and streams the final ranked list back to the browser via SSE. The agent dialogue feed in the UI shows every inter-agent message in real time so you can watch the pipeline think.

python3 -m venv .venv

bash 
# Create/edit ~/.aws/credentials
[bedrock-deployer]
aws_access_key_id     = YOUR_ACCESS_KEY
aws_secret_access_key = YOUR_SECRET_KEY
region                = us-east-1

Or use aws configure --profile bedrock-deployer.

3. Set environment variables

bash 
export AWS_PROFILE=bedrock-deployer
export AWS_REGION=us-east-1
export MODEL_ID=us.anthropic.claude-haiku-4-5-20251001-v1:0   # us. prefix REQUIRED
export MODEL_ID_TOOLS=amazon.nova-micro-v1:0                  # Nova Micro for theme extraction

The us. prefix on MODEL_ID is mandatory. Omitting it causes a ValidationException from the Bedrock API. This is the cross-region inference prefix.

4. Run the Flask server

bash
python app.py

Open http://localhost:5050 in your browser.

5. Run your first search

  1. Type a product query (e.g., wireless earbuds)
  2. Select a marketplace (e.g., US ($))
  3. Optionally adjust the review window (default 90 days)
  4. Click Analyze
  5. Watch the agent dialogue feed stream in real time — results appear in ~50 seconds

Review Window Feature

The review window controls how far back in time reviews are considered by Agent 2 (Review Intelligence). This is a first-class feature with several implications:

SettingRangeDefault
REVIEW_WINDOW_DAYS env var7–366 days90 days
Per-request override7–366 daysUses env var default

How the window affects the pipeline

  1. Discovery (Agent 1): The Trending tier gate counts "recent reviews" within the window. A product with 10 reviews in the past 7 days may qualify as Trending on a short window but not on a long one.
  2. Review Intelligence (Agent 2): Only reviews posted within the window are sent to the LLM for sentiment analysis. This keeps analysis focused on the most current customer sentiment.
  3. Daily cache keying: The cache key includes the window value. Searching for wireless earbuds / US / 30 days and wireless earbuds / US / 90 days produce separate cache entries — they do not collide.

Choosing a window

Use caseRecommended window
Catching viral / newly trending products7–14 days
General product research90 days (default)
Long-term quality assessment180–366 days

FinOps & Cost Management

Julie has three layers of cost control, and uses the cheapest available model for each task to keep per-query costs well under a cent.

🛡️

1. Daily budget guard

Set by DAILY_COST_BUDGET_USD (default $5.00). finops/budget.py tracks Bedrock API spend per UTC day. Once exhausted, the platform returns cached results only or declines new LLM calls until midnight UTC.

♻️

2. Daily result cache

finops/daily_cache.py caches complete pipeline results keyed by query + marketplace + review_window_days. Valid for the UTC calendar day; a repeat search costs $0 in Bedrock tokens. EventBridge flushes the S3 cache at 00:05 UTC daily.

🔻

3. Token optimisation

finops/pricing.py estimates token cost before each LLM call. Reviews are truncated or batched to stay within per-call token budgets. Validated by test_token_optimization.py.

Troubleshooting

ValidationException from Bedrock

error
ValidationException: The provided model identifier is invalid.

Cause: MODEL_ID is missing the us. cross-region inference prefix.

Fix:

bash 
export MODEL_ID=us.anthropic.claude-haiku-4-5-20251001-v1:0
#                ^^ this prefix is REQUIRED

Empty search results

Symptom: The UI shows "No products found" or the discovery agent returns an empty list.

Causes & fixes:

CauseFix
Amazon rate-limiting your IPThe scraper automatically retries with a fresh session. Wait 30–60 seconds and try again.
ChromeDriver version mismatchRun google-chrome --version and chromedriver --version — major versions must match.
Network/proxy blockingTry a different network. Some corporate networks block headless browser traffic.
Query too nicheTry a broader search term.

Chrome / ChromeDriver not found

error
WebDriverException: 'chromedriver' executable needs to be in PATH

Fix:

bash 
# macOS
brew install --cask chromedriver
xattr -d com.apple.quarantine $(which chromedriver)   # remove Gatekeeper quarantine

# Ubuntu
sudo apt-get install -y chromium-driver

Bedrock access denied

error
AccessDeniedException: User is not authorized to perform: bedrock:InvokeModel

Fixes:

  1. Confirm you are using the bedrock-deployer profile: export AWS_PROFILE=bedrock-deployer
  2. Confirm the IAM user/role has bedrock:InvokeModel permission in us-east-1
  3. Confirm Claude Haiku 4.5 and Nova Micro are enabled in the Bedrock console → Model Access page (Account YOUR_AWS_ACCOUNT_ID, us-east-1)

LLM calls fall back to mock responses

This is expected behaviour when Bedrock is unreachable (e.g., no AWS credentials, network issue, or budget exhausted). Julie continues to return product results — they will just lack LLM-generated review summaries. Check the server logs for [MOCK] or [FALLBACK] messages.

Daily budget exhausted

error
BudgetExhaustedError: Daily Bedrock budget of $5.00 exceeded

Options:

  • Wait until midnight UTC for the budget to reset
  • Increase DAILY_COST_BUDGET_USD and restart the server
  • Use cached results (repeat a previous search with the same query + marketplace + window)

AI Security Measures

ThreatMitigation
Prompt injection via reviewsReview text is passed as data within a structured prompt template — never as system instructions. The LLM is instructed to "use only supplied evidence" and "respond with ONLY raw JSON."
Cost explosion (token flooding)Daily budget guard ($5 cap), per-star sampling caps (max 33 reviews per ASIN), max_tokens=300 on LLM calls, automatic mock fallback on budget breach.

Part 2: Interview Questions (Techno-Functional)

Category 1: AI Agent Orchestration (6 questions)

  1. Walk me through the 4-stage pipeline. Which stages are true AI agents and which are processing stages?
    Answer direction

    Stages 1 (Discovery) and 3 (Price & Rating) are pure Python processing — no LLM involved. Stage 2 (Review Intelligence) uses Nova Micro for theme extraction; Stage 4 (Recommendation) uses Claude Haiku for reasoning and narrative generation. This distinction matters for cost and latency: LLM calls are reserved for where genuine reasoning is needed, keeping per-search cost under $0.005.

  2. Why did you choose a sequential pipeline rather than parallel agent execution?
    Answer direction

    Each stage depends on the previous stage's output — Discovery provides ASINs to Review Intelligence, which feeds Price & Rating normalization, which feeds Recommendation scoring. True cross-stage parallelism would require complex coordination overhead. The I/O-heavy work (Chrome scraping) is already parallelized within Discovery via multi-tab loading, which is where the real latency savings are.

  3. How does the Discovery stage decide which products are "trending" vs "best sellers"?
    Answer direction

    Discovery uses tiered CSS selector logic: first checks for "Best Seller" badge elements, then "#1 New Release" badges, then falls back to position-based ranking from search results. Products with a monthly-purchases data attribute above a threshold are flagged as trending. Sponsored tiles are filtered unless they carry real rating/review data (the organic-data pass-through rule).

  4. What happens if the LLM returns malformed JSON in the Review Intelligence stage?
    Answer direction

    A 3-step fallback fires: strip markdown code fences → attempt json.loads → extract outermost {...} block via regex. If all three fail, the stage returns a deterministic MockProvider response with generic theme labels. The pipeline never hard-stops on LLM output failures — this is also why the budget guard returns mock data rather than raising an exception.

  5. How would you add a 5th stage (e.g., competitor comparison) without disrupting existing stages?
    Answer direction

    The pipeline is a list of stage functions in agents/pipeline.py, each following the same interface: accepts a list of Product dataclass instances and returns an enriched list. Adding a stage means implementing that interface, appending it to the pipeline list, and accounting for its cost in the budget guard. No changes to existing stages are required.

  6. Explain how your AgentCore Runtime and Gateway are configured in CloudFormation.
    Answer direction

    The CloudFormation template in cloudformation/ defines AWS::BedrockAgentCoreRuntime::Runtime and AWS::BedrockAgentCoreGateway::Gateway resources wired together via stack outputs and imports. The Strands SDK pattern in agentcore/ provides a local development harness that mirrors the CloudFormation-deployed version, enabling local testing without a full AWS deployment cycle.

Category 2: Observability & Alerting (5 questions)

  1. You have 3 CloudWatch alarms. Walk me through each — what triggers them and what action is taken?
    Answer direction

    (1) High Error Rate — error log count exceeds threshold in a 5-minute window, SNS notifies. (2) Budget Breach — daily spend metric exceeds $5, SNS notifies and mock fallback activates automatically. (3) High Latency — pipeline duration metric exceeds threshold. All three route notifications through the SNS topic defined in observability/.

  2. How do structured logs flow from your Flask app to CloudWatch, and how do Metric Filters extract custom metrics?
    Answer direction

    The Flask app uses Python's logging module with a JSON formatter outputting structured records (timestamp, level, event, cost, latency) to stdout. The CloudWatch agent captures stdout and routes it to the Log Group. Metric Filters in observability/ use JSON filter patterns (e.g., { $.event = "llm_call" }) to extract numeric values like cost_usd as custom CloudWatch metrics.

  3. If I wanted to add a latency alarm (P95 > 60s), how would you implement it?
    Answer direction

    Add a Metric Filter on the structured log field duration_seconds in observability/cloudwatch.yaml, then create a CloudWatch Alarm on that metric with ExtendedStatistics: p95 and a threshold of 60. Wire the alarm action to the existing SNS topic. The Flask app already logs duration_seconds per pipeline run, so no application code changes are needed.

  4. Why SNS for alerting rather than directly invoking a Lambda or posting to Slack?
    Answer direction

    SNS provides decoupled fan-out — a single alarm can notify email, Slack (via Lambda subscriber), and PagerDuty simultaneously without coupling the alarm to any specific downstream. Adding a new notification channel requires only a new SNS subscription, not a CloudFormation template change. It's also the AWS-native pattern for CloudWatch alarm actions.

  5. How would you debug a situation where alarms aren't firing even though errors are occurring?
    Answer direction

    First verify logs are arriving: use CloudWatch Logs Insights to query the log group. Then verify the Metric Filter pattern still matches the log format (a schema change can silently break extraction). Then check whether the metric has data points in the CloudWatch Metrics console. Finally verify the alarm's comparison operator, period, and evaluation periods. Broken JSON log formatting is the most common silent failure.

Category 3: FinOps / Billing (5 questions)

  1. Explain your two-model cost strategy. Why Nova Micro for themes and Haiku for recommendations?
    Answer direction

    Nova Micro is $0.035/1M tokens — used for theme extraction, which is essentially pattern matching across short review text. Claude Haiku is $1/1M tokens (29× more expensive) but handles reasoning and narrative synthesis — used only in the Recommendation stage. Total per-search LLM cost is ~$0.004 vs ~$0.008 if Haiku were used throughout, cutting the effective daily budget ceiling in half.

  2. Walk me through the daily budget guard. What happens at $5.01 spend? Does the service go down?
    Answer direction

    The budget guard in finops/budget_guard.py tracks cumulative spend in a daily-keyed file. When is_budget_exhausted() returns True, the @budget_guard decorator on LLM calls returns the MockProvider response instead of hitting Bedrock. The Flask service stays up and returns results — they're deterministic mock data rather than live LLM output. The user gets a valid response; no 503 is ever returned.

  3. How does the daily cache save money? What's the cache key, and when does it invalidate?
    Answer direction

    The cache key is f"{query}:{review_window_days}:{country}:{utc_date}". A repeat search within the same UTC day returns the cached result at zero LLM cost. Cache invalidates automatically at midnight UTC (new date in key). Different review windows produce different keys — a 7-day and a 90-day search for the same product are cached independently, preventing stale cross-window contamination.

  4. If token costs doubled tomorrow, what would you change in your architecture?
    Answer direction

    Tighten the sampling caps (max reviews per ASIN, character truncation per review) in agents/review_intelligence.py. Lower the daily budget cap. Route more tasks to Nova Micro or introduce Nova Lite for the theme stage. Update model_pricing.json to reflect new costs so budget tracking remains accurate. The modular model selection means no structural changes — just config and sampling parameters.

  5. How do you track per-request cost in real time? Where is it logged and how could you build a dashboard?
    Answer direction

    Each LLM call logs {"event": "llm_call", "model": "...", "input_tokens": N, "output_tokens": N, "cost_usd": X} as structured JSON. The pipeline accumulates this into pipeline_run.cost_usd. A CloudWatch dashboard can use the existing Metric Filter on cost_usd to display daily spend trend, per-model cost breakdown, and budget utilization percentage — all without application code changes.

Category 4: Python Automation (5 questions)

  1. Explain the multi-tab parallel browser approach. Why is it faster than sequential?
    Answer direction

    The scraper opens N tabs simultaneously using driver.execute_script("window.open()") and switches to each to initiate navigation. With page_load_strategy='eager', each tab reaches DOM-interactive independently — Chrome handles the parallel HTTP requests. Sequential loading waits for each page to fully load before starting the next (~3 min for 5 products). Multi-tab reduces this to the time of the slowest single page (~50s).

  2. How do signal handlers prevent zombie Chrome processes? Walk me through the atexit + SIGTERM pattern.
    Answer direction

    atexit.register(cleanup) fires on normal Python exit. signal.signal(SIGTERM, handler) catches OS termination signals (e.g., when Flask is killed by a process manager). Both call driver.quit() on all browsers tracked in a weakref.WeakSet. The WeakSet means already-garbage-collected browser objects don't block cleanup, preventing orphaned Chrome processes after Flask restarts or mid-request crashes.

  3. How does your price parser handle different locale formats ($1,234.56 vs 1.234,56€)?
    Answer direction

    The parser extracts the numeric string via regex, then detects locale by checking whether the last separator is a comma or period. If the pattern matches European format (period for thousands, comma for decimal), it swaps separators before calling float(). The currency symbol is extracted separately as the first or last non-numeric, non-separator character — not inferred from the marketplace domain, which Amazon overrides by geo-IP.

  4. Why did you use page_load_strategy='eager' instead of 'normal'? What are the tradeoffs?
    Answer direction

    'eager' waits for DOM-interactive (HTML parsed, critical JS loaded) rather than all resources including images and tracking pixels. Amazon product pages have heavy assets that add 2–5 seconds per page. The tradeoff: if price/rating data is injected by late-loading JavaScript, 'eager' could miss it. Testing confirmed Amazon's key data attributes are in the initial HTML, making 'eager' safe for this specific use case.

  5. How would you make this scraper more resilient to Amazon's rate limiting?
    Answer direction

    Add exponential backoff with jitter on 503/429 responses. Randomize inter-tab delay (1–3s random sleep). Implement a circuit breaker that stops retrying after N failures and returns cached results or mock data. The current design already fails gracefully (returns empty product list on scrape failure) — adding retry-with-backoff logic would improve resilience without breaking the graceful-degradation contract.

Category 5: LLM Knowledge (5 questions)

  1. Why does MODEL_ID need the 'us.' prefix? What is a cross-region inference profile?
    Answer direction

    Amazon Bedrock cross-region inference profiles (us., eu., ap. prefixes) route requests to available capacity across multiple AWS regions within that geographic boundary. This improves availability during regional capacity constraints. Without the prefix you're locked to a single region's throughput. The profile us.anthropic.claude-haiku-4-5 transparently routes across us-east-1, us-west-2, etc.

  2. Explain your token optimization pipeline. How do you achieve 60–70% reduction before sending to the LLM?
    Answer direction

    Three steps: (1) Review sampling — max 33 reviews per ASIN, selected proportionally across star ratings (not just most recent). (2) Text truncation — each review body capped at 200 characters. (3) Field stripping — only rating, title, and body[:200] sent; reviewer name, date, verified purchase, and helpful-vote fields dropped. Together these reduce a typical 50-review dataset from ~15,000 tokens to ~4,000.

  3. Your system prompt says "respond with ONLY raw JSON." How does this protect against prompt injection from review text?
    Answer direction

    Review text is passed as data within a fixed JSON structure in the user message — never as free-form instructions. The system prompt establishes the LLM's role and output contract before any user data appears. A malicious review containing "ignore previous instructions" is just a string within the body field; the LLM's instruction hierarchy treats the system prompt as authoritative over content in the data payload.

  4. What's the difference between the Nova Micro and Anthropic request formats in your invoke() function?
    Answer direction

    Both use the Bedrock Converse API, which normalizes the interface across models. Nova Micro uses inferenceConfig.maxTokens; Anthropic Claude natively uses max_tokens — but the Converse API abstraction handles this transparently. The key practical difference is that Nova Micro's context window is smaller, which is why review sampling caps are especially important before routing to Nova Micro.

  5. If you needed to support Claude Sonnet for premium users, what would you change?
    Answer direction

    Update MODEL_ID to accept per-request model selection (already parameterized as an env var). Add a premium_model route parameter or user-tier check in the Flask route. Update model_pricing.json with Sonnet pricing for accurate budget tracking. Optionally increase max_tokens from 300 to 1024 for richer narratives. The Converse API abstraction means the invoke() function itself needs no changes.

Category 6: Architecture & Security (4 questions)

  1. How do you prevent XSS when rendering LLM-generated content in the browser?
    Answer direction

    All dynamic content — LLM-generated themes, product titles, descriptions — passes through escHtml() before DOM insertion, replacing <, >, &, ", and ' with HTML entities. innerHTML is never used with raw API response data. LLM output is also JSON schema-validated (expected keys only) before any rendering occurs.

  2. What validations exist on user input? Walk me through the review_window_days validation.
    Answer direction

    The Flask route uses request.args.get('review_window_days', 30, type=int); non-integer values fall back to default. The value is then validated as 7 ≤ value ≤ 366: below 7 is too fresh (insufficient reviews), above 366 exceeds one year (cache reliability degrades). Out-of-range values return HTTP 400 with a specific message. Country codes are validated against the AMAZON_DOMAINS allowlist (25 valid codes).

  3. If Amazon changes their page structure tomorrow, which parts break and how do you recover?
    Answer direction

    The Discovery stage CSS selectors are the most brittle and break first; price/rating extractors are second. The rest of the pipeline (Review Intelligence, Price normalization, Recommendation) is fully insulated — it consumes the structured Product dataclass, not raw HTML. Recovery: update CSS selectors for the new structure via browser DevTools — typically a 5–10 minute fix once the new selectors are identified.

  4. Why Flask with SSE rather than FastAPI with WebSockets?
    Answer direction

    SSE is unidirectional server→client — exactly what pipeline progress streaming needs. WebSockets add bidirectional overhead and require an async event loop that complicates Selenium's synchronous blocking calls. Flask's Response(stream_with_context(...)) makes SSE trivial to implement. The browser's native EventSource API handles reconnection automatically — no client library required. FastAPI would add complexity without any functional benefit here.
